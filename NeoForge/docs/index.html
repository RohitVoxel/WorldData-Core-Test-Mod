WorldData Core Test Suite

ATM_PACK V1 - a realistic, ops-count-driven stress test for WorldData Core, compared call by call with plain Minecraft. NeoForge 21.1, Minecraft 1.21.1, Java 21.

What it does

One run is one number you choose: how many ops to complete (default 200,000). The run has no time limit and no scale knobs. It ends when completed ops reach that total, then a drain settles everything still in flight. Wall time is a result, not a setting.

The ops are issued in batches of at most 8,000, one batch after another with no pause in between, and the test mod itself is held to a small time budget per server tick (3 ms by default) so it cannot starve the game. Chunk loading is done by Minecraft only, in 60 waves of 1 to 64 chunks per full run, and no batch ever waits for a wave. WorldData Core is never asked to load a chunk and its diagnostics are never called: the Core arm only reads what Minecraft has loaded.

The same seeded plan runs on two sides: Minecraft (ServerLevel only; chosen with run vanilla, or picked automatically when WorldData Core is not installed) and WorldData Core (reads through its public API, writes through Minecraft, plus a paired Minecraft baseline sampled on the same coordinates, one read in 32 of an action, one in 256 for chunk, box and grid scans, plus the first 64 successful samples of every action and 16 for the scans, so p50 and p99 stay valid while the baseline stays cheap). The report shows both sides, the time each took to finish all ops and the sample policy.

Quick start

1. Build the Core:      WorldData_Core_NeoForge.zip  ->  build/libs/worlddata_core-1.0.0.jar
2. Copy the jar to:     worlddata-test-suite/libs/worlddata_core-1.0.0.jar
3. ./gradlew build      (worlddata-test-suite/build/libs/worlddata-core-test-suite-0.1.0.jar)
4. Put both jars in mods/ and open a THROWAWAY world (the run edits blocks in a sky arena and restores them)
5. /worlddatatest run                    (200,000 ops, no ops per second cap)
   /worlddatatest run 500000             (ops)
   /worlddatatest run 500000 40000       (ops, opsPerSec: send at most 40000 ops per second; 0 or left out = no cap)
   /worlddatatest run 500000 40000 4     (ops, opsPerSec, tickMs: test mod time per server tick, 1 to 5 ms, default 3)
   /worlddatatest run 500000 40000 4 42  (ops, opsPerSec, tickMs, seed)
   /worlddatatest run vanilla 200000     (source first: Minecraft only, no restart needed)
   /worlddatatest run core 200000        (source first: WorldData Core)

How a run works

The test mod never holds ops

Each planned issue is a pure function of (seed, index). It is handed to WorldData Core (or Minecraft) the moment it is drawn and the answer decides its outcome: PASS, UNLOADED, UNAVAILABLE, TIMEOUT or FAIL. If the answer is "not ready yet" the harness keeps only a reference (chunk token, issue time) and polls the side's own status (the Core's availability, Minecraft's chunk state) until it is terminal. There is no local queue, no local waiting loop and no local retry.

Batches, one after another, no pause

  • The total is cut into batches. A batch is at most 8,000 ops (hard cap) and at least 400 (except a tiny run). Sizes are dynamic and seeded: they average a 200th of the total (800 to 8,000) and vary between half and one and a half times that, so both arms get the same batches.
  • Batches are sequential and never wait for each other's answers. Batch N+1 opens as soon as every op of batch N has been issued, in the same tick if budget remains, so there is no designed pause between ops or between batches (0 ticks, reported). An op whose answer is \"not ready yet\" leaves the batch as a reference on a side lane and settles there: it is polled in the background and ends as PASS, UNLOADED, UNAVAILABLE, FAIL or, only if nothing answered for 90 s, a watchdog TIMEOUT counted on its own line. A slow chunk load therefore never stalls the next batch; the report counts how many batches opened while something was still waiting.
  • Each batch has its own mix: the base shares below are scaled by a seeded factor per kind and one theme kind is boosted, so batches differ from each other while the run average stays on the base shares.

Ops per second cap

The opsPerSec argument limits how many counted ops the test mod issues. Left out, or 0, nothing is paced and the run goes as fast as the per-tick time budget allows. With a value, a token bucket paces the ops smoothly across ticks and a sliding one-second window guarantees that no one-second window of ticks holds more than the cap (the report shows the peak). The cap has no upper limit of its own: with 200,000 total ops, a cap of 200,000 is allowed and the run can finish in about a second if the time budget lets it. The cap counts ops as the run counts them; the 16-thread contention probe, the background polls and the Minecraft baseline reads are outside the ops count. Ticks held back by the cap are counted separately and never count as idle ticks with work left. The report shows the cap, the average ops per second and the peak in any one second.

Dimensions and heights

A run starts in the dimension of the command source. The read Y range and the sky arena are derived from that dimension's height, so shorter, taller or custom dimensions are handled; the standard overworld keeps y 40 to 95 for reads and y 232 to 239 for the arena. Modded blocks and biomes are read through the same registry ids as vanilla ones.

The per-tick time budget

Every server tick the harness may work only until its time budget is spent: 3 ms by default, set with the tickMs argument of the run command (whole milliseconds, 1 to 5; anything else is refused by the command). The clock is System.nanoTime(), checked before every op, so a batch is spread over as many ticks as it needs and never runs as one big loop. The budget covers everything the test mod does on the server thread: polling the status of waiting references (at most 40 % of the budget), the Minecraft ticket calls and releases of the waves, the read ops themselves, the 16-thread contention probe and the allocation sample. At least one op is issued per tick so a run always progresses. This is the only protection of the tick rate; there is no feedback loop on MSPT. The report shows the real harness time per tick (mean / p50 / p99 / max).

Thrash workers per batch (16 by default, up to 64)

Every op of a batch belongs to one of the logical workers (16 by default; round robin, so each gets an equal share). About 40 % of the point, layer and filter reads of a batch go to 16 shared cells of the pinned hotspot chunks with the same call and the same coordinates, so several workers read the same position within a tick; the rest use coordinates of their own. Reads of the same cell with the same call in the same tick must return the same digest; any disagreement is counted. The report lists ops, shared-coordinate ops and not-passed ops for each worker. Separately, every 8th batch a contention probe runs one real thread per worker (16 by default) on the same cells, synchronously inside the tick (so no write can race them), and compares their digests and speed with one thread. The probe is not counted in the ops total, and its reads per thread shrink from 256 down to 32 if it ever costs more than half the budget. World writes stay on the server thread.

The worker count is the fifth argument of the run command, run [ops] [opsPerSec] [tickMs] [seed] [thrash]: 16 by default, any whole number from 16 to 64. It sets the logical workers of every batch and the real threads of the contention probe; the 16 shared cells and the 40 % stay the same. A wider thrash changes which worker gets which op, so compare runs only with the same thrash value. ramp and efficiency take the same value as thrash=16|32|64 (on means 16); it is off there by default.

Force-load waves: Minecraft only, 60 per run

Chunks are loaded with Minecraft's own region tickets (ServerChunkCache.addRegionTicket and removeRegionTicket), the same way in both arms. In the Core arm WorldData Core never receives a load request of any kind; it only reads chunks after Minecraft has loaded them. The waves run beside the batches, never inside them:

  • 60 waves on a full run (120,000 ops or more). A shorter run scales the count down (one wave per 2,000 ops, at least one). Waves start when the op cursor passes a seeded trigger spread over the first 90 % of the run, and the run only ends after the last started wave has finished.
  • Every wave loads 1 to 64 chunks, drawn uniformly, a different size each time. A wave is a rectangle of chunks submitted as a few small ticket calls (at most 16 chunks per call) plus up to seven single chunks that also use a chunk future. The future is requested from a helper thread, because ServerChunkCache.getChunkFuture called on the server thread parks it until the chunk is ready.
  • Waves reuse chunks: they are cut from a bounded pool of 32 x 32 chunks around 12 seeded anchors, so later waves revisit the chunks of earlier ones (this is what measures reload after release). The reader refuses to touch more than 1,500 unique chunks (hotspots included) or more than 4,096 ticket calls; refusals are counted, and a normal run stays far below both.
  • Each wave is held for 20 ticks after all its chunks are loaded so reads can hit them, then its tickets are removed so the chunks can unload. Tickets are reference counted per chunk, so overlapping waves share a ticket and only the last release removes it. Everything still held is released when the run ends, and the report shows request calls, release calls and tickets still held (they must match and be zero).
  • A wave that never finishes does not block anything; after 90 s its group is counted as timed out and released.
  • The server thread never waits for a load. Submitting a group only adds tickets and, for a single chunk, hands the future request to the helper thread. Readiness is polled once per tick, never in the tick the group was submitted, and only while the poll share of the tick budget lasts. A chunk counts as ready when ServerChunkCache.getChunkNow returns it (loaded to FULL), not when hasChunk says its ticket level allows it. The reads of both arms check this before getChunk so that no read can park the server thread on a chunk that is still loading. The time a future takes to complete is recorded when it completes, not when it is polled.
  • The 24 hotspot chunks (6 clusters of 2x2) are pinned with Minecraft tickets in 9 calls at the start and stay pinned for the whole run; they are released when the run ends. They are not part of the 60 waves.
  • Reads that are not aimed at hotspots go to the chunks of the most recently started wave, so they meet chunks that are loading, loaded or already released.

The block lookup kind uses the Core's lookup by tag, name and state id and its registry facade. The Minecraft side does the same work with BlockState.is over the chunk (tags, blocks and state-id sets), BuiltInRegistries.BLOCK, Block.getId / stateById and a registry tag walk. Names, tags and state tags come from one fixed set shared by both arms (LookupSet). A by-state-id read answers UNAVAILABLE on the Core side until the Core has seen a state of one of those blocks. Chunk scans and the tag walk are sampled as heavy baselines.

These are all the WorldData Core calls the suite makes: query calls only, each timed on its own. There is no call that loads, pins or releases a chunk on the Core, and no call to its diagnostics. The test mod's own metrics (counters, latency tables, caches of what it saw) are kept inside the test mod.

Throttle ramp and efficiency

Two extra commands measure speed in a stable area. Both only read, use the same op mix and seed on both arms, work in any dimension, and have no gates: the report only shows measured numbers. Run them in a loaded, unchanging area, standing still, with the same world, dimension, seed and spot for every arm you compare.

The ops are the pack read mix (point, layer, filter, spatial, biome / availability / raw / peek / world snapshot) on the 24 pinned hotspot chunks. There are no force-load waves, no writes and no light reads (the pack run issues those from the client tick on an integrated server; these modes do not). The Minecraft arm uses Minecraft APIs only; the WorldData Core arm uses the Core public API only, with no paired Minecraft baseline. arm=auto uses Core when it is installed; vanilla forces the Minecraft arm even with Core installed (Core is then not queried, but its own tick work still runs), so both arms can be compared on one install. The load across arms is not assumed identical, and the report says so.

Throttle ramp: ramp <targetMs> [seed] [overMs=10] [holdTicks=100] [startOps=100] [stepOps=100] [tickIssueMs]

Ops per second start at startOps and rise by stepOps every second of wall clock. Each tick gets a token bucket share of the current rate (at most about 100 ms of tokens, so a long tick cannot cause a burst). The run stops when server MSPT (tick start to tick end, which includes the test mod's own issue time) stays above targetMs + overMs for holdTicks ticks in a row. A few natural spikes never stop it; they are counted. With tickIssueMs set, no more than that many ms are spent issuing in one tick and the remaining intended ops are dropped and counted; left out, every intended op is issued however long it takes (50 ms is only a reference when you read MSPT).

More options as name=value (any order): stepSeconds=1, maxOps=5000000 (ceiling, held for twice the hold window, then the run ends), maxMinutes=60, packBaselineMs (idle MSPT of your pack, only quoted in the report), coreBudgetMs (recorded as stated), thrash=on|16|32|64 (a burst of that many real threads every 20 ticks, outside the measured window; on is 16; off by default; efficiency takes it too), arm=auto|core|vanilla, note=text. The report gives the last step before MSPT stayed above the stop level and the step where it started to, intended and achieved ops/s, MSPT and issue time for the whole run and the final window, outcomes, how the tick time splits between the issue loop and the rest, per-second timeline.csv and per-tick ticks.csv. With +100 ops/s per second a fast reader needs a long time to reach a high rate; raise stepOps for a quicker ramp.

Efficiency: efficiency <arm|auto> [windowMs=1.0] [ticks=300] [seed] [coreBudgetMs] [safetyMs] [holdTicks=100] [warmup=60]

Each tick, after a warm-up, a fixed window of windowMs of measured op time on the server thread is opened and ops are issued until it is used up; the report counts how many useful (PASS) ops completed per ms. Warm-up runs at least warmup ticks and until no read has been pending for the last ticks of it. Pending ops are not counted as completed. The window length is measured, not assumed: ops per ms always uses the measured window, and the report gives the overshoot (the last op ends after the deadline) and the clock-read cost per op. It also gives ops per window, PASS rate, a per-read-action table (ops per ms of each action), MSPT for context and per-call latency. safetyMs (default 100) stops the run if the mean MSPT over holdTicks ticks stays above it.

The test mod cannot read or set WorldData Core's budget through the public API. coreBudgetMs (default 4, Core's own default) is recorded as stated, so set the real value first with /worlddata budget fixed <ms> and pass the same number; "Core budget used" is shown as not exposed.

When the other arm has been run before (same mode), each report adds a Core vs Minecraft table with the ratio, and says if the two runs used different settings. The last result of each arm is kept in the reports folder. Files per run: report.md, report.json, ticks.csv, latency.csv, plus timeline.csv (ramp) or actions.csv (efficiency). stop ends either run early and still writes its report; status shows its progress.

The report

Files per run: report.json, report.md (the short report), report.csv (one wide row, latency_<api>_p50_ns and friends), latency.csv (one row per API), curve.csv (completed ops, in flight, tick time, batch size, batch number and harness time over time) and sink.bin (the data the DataSink consumed).

The block-write check used to be printed as a "pipeline drift audit". It was removed from the default report because it compared Minecraft's minecraft:air with what Core stores for air (Core keeps every air variant as empty, so it has no block id for it), which turned every position whose last write was air into a false mismatch. The comparison now treats all air variants as one block and counts unreadable positions apart, and the result stays in report.json as a diagnostic.

What is not measured, and why

  • Core's spill timer: internal to the Core and not exposed by its public API. The reload time of reused chunks is shown for both sides when both have a finished run with the same ops and seed.
  • Core's own tick budget: it is set with the Core's own command and is not an input of this suite; the report shows MSPT for whatever the Core is configured to.
  • Short or cold runs: the first ticks of a run run cold code, so the harness time per tick is meaningful from a few hundred ticks on, not for a run of a few seconds.
  • Spatial calls are plain reads; an incomplete coverage counts as UNLOADED on both sides.

Threads

Everything runs on the server thread except: light reads (on an integrated server the pack run issues them from the client tick, under the same time budget, because the Core answers light live from the thread that owns the level and the client thread owns the client level; on a dedicated server they run on the server thread), the 16 contention probe threads (run synchronously inside the tick so no write can race them), and the DataSink IO thread (budgeted, never blocks a tick).

Updating the design

Send the updated design file and say the design changed. The constants live in one place, PackConfig (batch cap, tick budget, worker count, wave limits); the base op mix in OpKind, the per-batch mix in BatchProfile and the per-op plan in IssuePlan; the batch sizes in BatchPlanner; the wave count, triggers and chunk sets in WaveSchedule and WavePlan, the wave lifecycle in WaveRunner, the Minecraft ticket calls in VanillaWorldReader; the gates in PackReportBuilder.
